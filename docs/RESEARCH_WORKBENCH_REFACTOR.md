# 科研工作台端到端重构方案

日期：2026-09-29。状态：设计草案，待确认；不是已实现能力说明。

## 1. 产品目标与非目标

帮助研究者把一个明确的研究工作单元做成可检查、可修改、可复现的产物。自然语言是入口和操作方式，研究对象与实际结果是工作台主体，报告只是交付形式之一。

- 不要求用户先懂分类、工具、编程语言或统计模型；不强制填写统一长表。
- 不以 AI 自评、Skill 数量、工具调用成功或审查通过证明科学正确。
- 不承诺一个通用流程能自动完成任意研究，更不承诺发表、显著性或预期结论。
- 本次优先重构目标、状态、分支、验证和返修契约；不先扩充 MCP、语言、数据库或专业算法。
- 不大爆炸替换：新任务使用版本化新框架，旧任务留在原执行器；原数据库与产物不被试验代码改写。

## 2. 现状与结构性问题

代码锚点：frontend/src/App.tsx 的研究问题入口；internal/app/workflow/starter.go 的 StartResearchCommand；research_routes.go 的阶段目录和语义路线编译；dynamic_route.go 的分支与工具分配；runtime.go 的执行、审查与返修；templates.go 的固定分析模板。

现有基础可复用：持久工作流、冻结输入与引用、任务资料隔离、工具审批、Python 环境与产物、审查快照、自然语言返修和版本保存。

需要改变：

1. 通用阶段组合代替了领域工作契约，能编译不等于能完成研究目标。
2. 问题、方法、证据、结果散落在对话和阶段 JSON 中，用户很难持续核对。
3. 执行完成与交付完成混杂；失败既可能是服务错误，也可能是科学问题尚未解决。
4. 正式报告发布依赖文献证据，不适合纯数据、纯设计等交付。
5. 返修主要按起点重排后续，尚非稳定的对象依赖失效机制。
6. AI 审查不能替代数值、引用、覆盖及研究设计专用检查。

## 3. 用户全过程

### 入口：表达目标，不选择工具

保留自然语言输入与材料添加，可给可点击例子但不强制分类。新建后立即获得持久任务身份，资料导入与解析显示真实状态。用户在准备阶段即可编辑目标，不因模型请求中断丢失材料和对话。

### 理解：明确本次工作单元

AI 从对话、用户选择和材料中提出任务意图，可组合多个方向；归类是候选解释，不是授权。程序用能力目录解析已有执行分支，未知或未实现方向返回具体缺口，不静默换成报告或方案。

只问会影响交付或方法且不能从材料读取的问题。尚无材料允许讨论和准备，不伪装成可执行状态。

### 约定：让用户知道交付是什么

展示可编辑的简短任务约定：目标、输入范围、预期产物、验收事项、重要假设及不能完成的部分。用户明确表达的要求直接继承；只在存在实质选择或副作用时要求确认，不重复确认已选资料。

程序校验能力、输入、环境及权限。AI 不能删减原要求以通过检查。接受有限草稿是另一个交付目标的显式修订，不等于原任务完成。

### 工作：围绕可检查的中间产物推进

文献任务优先展示证据表，数据任务优先展示数据字典与结果，设计任务优先展示方案要素。不要求用户阅读工具日志才能知道进度。可在授权范围内有界补读、补查、纠错；换目标、改关键方法、扩展材料权限需确认修订。

### 核验：多个检查来源，不只一次 AI 回答

区分程序检查、数值检查、AI 语义复核和研究者决定，每项记录实际依据与未检查部分。未实现的检查不显示通过。没有致命问题不等于全部完成，产物须覆盖任务约定。

### 交付：产物与完成声明分开

展示具体文件/表/图/方案、满足与未满足项、来源与方法、复现信息。可交付部分成果，但清楚标为部分完成。保存检查点、导出、正式登记分别处理；登记需用户操作，不由模型自动代替。

### 返修：修改研究对象，产生新修订

用户自然语言或直接编辑提出修改；生成明确差异及受影响对象。确认后只重算依赖闭包，旧产物不可变，新产物重新验证。无可靠依赖映射时保守重跑相关分支及下游，不能猜测“无需重算”。已登记报告可作为新修订来源，不能原地覆盖。

## 4. 核心对象与状态

只引入承载真实行为的最小对象，不先做庞大的通用科研本体。

| 对象 | 作用 |
| --- | --- |
| ResearchTask | 持续的研究工作身份、项目归属、对话与当前修订 |
| TaskContract | 版本化目标、范围、交付要求、用户决定、验收清单 |
| MaterialVersion | 原始资料/数据、来源、哈希、解析状态与适用范围 |
| ResearchObject | 带类型与 schema 版本的证据表、变量字典、方法方案、结果等 |
| WorkPlan | 有类型输入输出的依赖图、所用能力版本、预算和工具授权上限 |
| Run / Attempt | 一次执行及重试；不是研究任务或交付质量本身 |
| Finding / Check | 检查对象版本、规则、依据、严重程度、修复或人工处理方式 |
| DeliverableVersion | 内容、依赖快照、验证结果、导出与登记状态 |

三套状态分离：

- 执行：queued / running / waiting_user / paused / failed / cancelled / completed。
- 研究对象有效性：current / stale / superseded；由依赖版本决定，不由 AI 自报。
- 交付：draft / needs_work / partial / ready；登记状态另存。ready 指符合该版本任务约定，不是科学正确认证。

约束：取消保留已保存结果；恢复不复活被取消的执行；用户修改时旧 Run 不得覆盖新修订；审查只适用于它实际核对的输入版本。模型、网络、解析、执行、契约与研究内容问题分开归因。

## 5. 研究分支与能力定义

内部采用任务工作类型，而非按学科硬拆。可描述的方向包括文献阅读、证据综合、研究设计、定量分析、质性分析、预测建模、仿真、专业数据分析及复现；列入分类不等于允许执行。

每个能力定义必须包含：id/version、适用工作与限制、输入/输出 schema、必需步骤、可选步骤、工具角色、环境适配器、权限与预算、检查策略、失效规则及验证案例。程序维护可用状态和验证依据，模型只能请求能力，不能创建或升级能力等级。

初期落地三类输出契约：

1. **文献证据工作**：材料 → 字段/主张与原文关联 → 覆盖及冲突记录 → 证据交付；未找到、无法读取、明确未报告分开。
2. **表格分析工作**：数据 → 变量/单位/实验单位/重复测量约定 → 方法与代码 → 计算及检查 → 结果交付。
3. **研究方案工作**：问题与约束 → 设计要素及前提 → 可执行性核对 → 方案交付，不生成虚假实证结果。

组合任务通过有类型对象连接，例如文献为分析提供背景，但不能把文献数值当本次计算输出。报告、数值表、图、代码、方案各有交付策略；纯数据任务不应为了保存报告被迫检索文献。

## 6. 工具、语言与规划边界

用户不必选择编程语言。能力定义选用可用执行适配器，目前优先复用已有 Python。R、Julia 等只有实现了环境检查、执行、超时取消、日志、输出收集和验证后才成为可执行适配器。

授权在编译时冻结上限，执行时按阶段提供最小工具集合；目录发现不授予执行权限。模型可在集合内调整检索词、补读和修复代码，不可通过改路线扩大网络、文件或执行权限。工具更新须重新校验绑定，旧快照不能被静默替换。

全程检查任务/project 范围与真实输入身份。预算至少覆盖调用次数、补查轮数、时长和上下文；费用仅在有可靠计价时显示估算，不能伪精确。预算耗尽保存检查点并说明剩余工作，不重新启动整任务规避预算。

## 7. 界面信息架构

一个任务工作区，按实际存在的对象展示，不强制所有任务出现所有页签：

- **概览**：当前目标、正在做什么、已有成果、还差什么、需要用户做什么。
- **资料与数据**：已选材料、版本、解析/质控问题、使用关系。
- **研究内容**：证据表、变量字典、方法方案等可检查对象。
- **结果与交付**：表图文件、检查结果、版本差异、导出与登记。
- 对话常驻，当前工具活动可见，历史过程折叠为辅助审计，不占据主要内容区。

提示应能回答下一步：是继续等待、补充资料、确认设计、修正方法还是重试服务。不把这些情况统称“处理中”或“科研失败”。

## 8. 核验与失败恢复

- 来源检查：身份、哈希、精确片段、定位与任务范围；语义支持另外核对。
- 覆盖检查：任务要求字段与实际成果对应，未检索到不推出全文不存在。
- 计算检查：可执行性、输出 schema、单位/范围/一致性；重要方法建立独立参考计算，未提供参考检查明确披露。
- 研究检查：前提、偏倚、替代解释、结论强度；自动检查、AI 和人工各留记录。
- 返修问题绑定对象版本和具体位置；给出可以执行的动作，不用空泛建议替代缺陷。
- 幂等与恢复：持久化检查点、事件去重、执行 CAS、孤立运行恢复、取消/重启/断流测试；旧结果不能覆盖新修订。

安全边界：语言运行环境不是强沙箱；新框架不可借“专业分支”绕过现有权限与路径检查。

## 9. 实施顺序与退出条件

### M0：契约与案例基线（先做）

确定对象 schema、状态迁移、能力接口、任务页交互与三个真实用户案例的输入/预期产物/失败行为。整理现有功能的保留、适配、替换清单；不把本草案视为完成实现。

退出条件：给定单篇论文比较、已有表格分析、无数据方案设计，能明确每个用户动作、状态和产物归属，解释停止、缺材料和返修如何闭环。

### M1：纵向最小闭环

先用文献比较实现自然语言入口 → 任务约定 → 可见证据对象 → 检查 → 交付 → 用户修改 → 新版本。接复用工具，不扩工具范围。

退出条件：真实任务验证目标未被偷偷改写、遗漏可定位、取消恢复、补材料更新、旧报告保留、无自动登记；同时包含失败案例，不只通路测试。

### M2：验证框架不是文献专用

接入现有表格与设计分支，使用各自对象、检查和交付策略。纯数据、纯设计均不强制文献发布链。

退出条件：固定数据的关键统计与参考结果一致；设计明确没有实证结果；复合任务的来源和计算结果不混用。没有足够检查依据的方法不默认开放。

### M3：切换新任务入口与专业扩展

完成新旧执行器分流、错误解释、交互与回归后切换新任务。旧任务可查看、导出并按旧规则执行，不伪迁移为新框架；从旧任务新建时显式复制授权材料与目标，重新验证。

新增方向须提供能力适配器、可用工具、产物及检查案例，不能仅增加 prompt 或分类卡片。

## 10. 验收矩阵

必须覆盖：材料缺失/不可读、检索漏项、引用不支持结论、错误单位、重复测量、缺失值、代码失败、网络中断、取消、重启、并发修改、权限拒绝、预算耗尽、返修和登记后版本保留。

分开记录：确定性单元与集成夹具、真实模型端到端、人工科研核对。指标包括字段正确率和遗漏率、关键数值一致率、引用支持率、错误发现与恢复、人工纠正次数和耗时。没有样本量与任务分布，不输出“科研覆盖百分比”。

## 11. 尚待设计决策

M0 必须具体化而非留到编码时猜：中间对象直接编辑与提案确认的边界；对象持久化与 schema 升级；安全的依赖失效粒度；不同类型 ready 判定；用户接受局限与修改原任务约定的区别；旧任务新建修订的资料复制规则。

本方案的重构单位是产品流程与任务契约，不要求重写可靠的底层模块。先让研究工作有可验证的状态，再增加工具。
